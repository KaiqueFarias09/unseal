# OPDS 2.0 test fixtures

Fixtures for the OPDS 2.0 JSON parser (`C05`). Three origins, all read-only
test data; the parser tests never fetch the network.

## Real independent catalogs (Feedbooks OPDS 2.0 test catalog)

`feedbooks-home.json`, `feedbooks-navigation.json`,
`feedbooks-publications.json` come from the Feedbooks OPDS test catalog,
published for client testing at
`https://feedbooks.github.io/opds-test-catalog/` (repo
`Feedbooks/opds-test-catalog`, branch `gh-pages`, commit
`d04db71d6151578db3101af5b28711b41d977300`, 2018-08-16). The catalog README
declares its purpose: "An OPDS catalog designed to test the features
supported by OPDS clients." The listed works are public-domain classics and
the feed content is bibliographic metadata about them. Files are stored
byte-identical to the source. Per-file SHA-256 values live in
`corpus-manifest.json`, which is the binding record.

## Canonical specification examples

`spec-*.json` were extracted from the OPDS 2.0 specification snapshot
`https://specs.opds.io/opds-2.0.html`
(SHA-256 `4946db3da773c7b63fd5dbb989c1ce64d6075a9a1da26070c8bf7fb9c6c46d85`,
fetched 2026-10-18) by parsing its `<pre>` blocks, HTML-unescaping, and
re-indenting with `json.dumps(..., indent=2, ensure_ascii=False)`. The
reformatting is the only transformation; keys and values are unchanged.
Names follow content, not section position:

- `spec-navigation-feed.json`, `spec-groups-feed.json`,
  `spec-groups-featured-feed.json`, `spec-paginated-feed.json` — complete
  feeds (navigation, groups, groups with a nested featured feed,
  pagination metadata with `rel` list `[first, previous]`).
- `spec-publications-feed.json` — complete feed whose single publication
  uses only `rel: download`. This canonical example violates the official
  `publication.schema.json` (no acquisition relation), which the corpus
  records as a negative case and `doc/opds2.md` documents as a
  schema-versus-text divergence.
- `spec-facets-fragment.json` — a facets-only fragment from the spec; not a
  complete feed, so the feed schema rejects it.
- `spec-search-link-basic.json`, `spec-search-link-query.json` — Link
  Object fragments showing the search URI template; validated against
  `link.schema.json`, not the feed schema.

## Authored synthetic fixtures

`synthetic-unicode-escapes.json`,
`synthetic-facets-groups.json`, `synthetic-acquisition-detail.json` were
authored for this mission to pin behavior the real feeds do not cover:
mixed-script titles with `\uXXXX` escapes, percent-encoded paths with query
and fragment parts, facets with titles, nested groups, subcollection
members, `rel` as array, price/indirectAcquisition/holds/copies/availability
properties, contributors as string/array/object, subjects, altIdentifier,
and the accessibility object. They are declared inputs, marked `synthetic-`
so no real catalog is implied.

`negative-*.json` and `normative-*.json` are minimal rejection fixtures:
`negative-` fails the pinned official schemas; `normative-` passes the
schemas but violates the normative text (facet title, search `{?query}`),
so the Dart parser must reject them separately from the schema reference.
`negative-truncated.json` is cut mid-value on purpose.

The corpus manifest `corpus-manifest.json` pins every file's SHA-256 and
classification; `tool/opds2_schema_oracle.py` refuses to run on changed
bytes. Expected parser outputs, generated by that same Python reference
(jsonschema 4.25.1 + referencing 0.37.0, CPython 3.12.14), live in
`expected/`.
